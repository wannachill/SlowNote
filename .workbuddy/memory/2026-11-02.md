## 思考内容不流式 + 尾部 final answer（诊断 + Stage 20 提示词）

用户反馈：思考内容和回答一起蹦出来、看不到思考的流式过程；思考末尾带 `final answer.`。

### 结论：不是渲染 bug，是请求架构

1. `_shared/llm.js` 发的是**非流式**请求（body 无 `stream: true`），DeepSeek 非流式下 reasoning 与 content 同批返回。
2. `wx.cloud.callFunction` **不支持流式返回**，云函数必须跑完再回整包。就算后端收上游的流，前端也拿不到增量。
3. 前端 `_requestAnswer` 里 `await call(...)` 拿到完整 reasoning 后一次性 setData，同一帧设上 `typingMessageId`，正文打字机立刻开始 → 观感就是"思考整块 + 正文逐字"同时起跑。

真流式唯一路径：云托管容器 + `wx.request` `enableChunked` + SSE + 从 `X-WX-OPENID` 重建鉴权/限流。成本过高，附录 A 只作记录。

### `final answer.` 来源

模型自己的思维链收尾标记（表示思考结束、转入正式回答），不是 SYSTEM 泄漏。清理只能放 `_shared/llm.js` 取到 reasoning 之后，**只锚尾部**，中段误删会读不通。清洗后为空要当"无思考"处理，否则留一个点开是空壳的思考块。

## 修复 aiSettings 400（userInfo 注入）+ Stage 22 提示词

### 根因：event.userInfo 被"多余字段"校验拦掉

`aiSettings/index.js` 原用 `Object.keys(event).some(key => key !== 'action')` 做严格白名单，但 `wx.cloud.callFunction` 会向 event 注入 `userInfo`（appId/openId），所以 get/save/reset **三个动作全部 400**，前端只拿到 `messages[400]`='请检查填写内容'，页面 catch 后又换成固定文案"设置暂时无法加载"，看起来像网络问题。

### 另一处会被暴露的样式 bug

`app.wxss:1056` 有 `.settings-page > .setting-card > .title { display: none }`（0,3,0），页面里的 `.setting-card > .title`（0,2,0）特异性更低 → **配置页六张卡片标题全被隐藏**。之前被 400 挡住看不到。修法：页面 wxss 把选择器提升到同等特异性（页面样式后加载，同特异性胜），不要用 `!important`，也别改全局。

## 诊断「小迈配置仍无法加载」：代码正确，云端是旧的

用 Node 打桩 `wx-server-sdk`（mock db + getWXContext）直接跑 `aiSettings` 的 main，六种入参全部返回 `code: 0`（get 空集合 / get 带 userInfo / save / save 后 get / reset / 非法 action→400）。本地代码与云端副本（diff `_shared` vs `lib`）一致，sync 清单已含 aiSettings。**结论：代码侧无问题，云端跑的不是这份代码。**

根因是前端把所有云侧失败统一包装成"网络慢"：`utils/api.js` 的 catch 对没有 `.code` 的错误（函数不存在 -501000、缺依赖 Cannot find module、超时）一律抛 `network: true`，页面 catch 再覆盖成"设置暂时无法加载，请检查网络后重试"。于是 400（旧版 userInfo 全等校验）、503、函数不存在三种完全不同的原因显示成同一句话。

### 改动

1. `utils/api.js`：networkError 上保留 `origin` 原始错误，不再丢弃 errMsg/errCode。
2. `pages/ai-settings/index.js`：新增 `failureHint(error)`，按 `Cannot find module` / `FunctionName|-501000` / 超时 / 400 / 401 / 503 分类给出具体原因，直接拼进错误文案。
3. `aiSettings/index.js`：`doc().set()` 包一层 `save()`，-502005 → `fail(501,'COLLECTION_MISSING')`；页面 `toastSaveError` 把 501 显示为"数据库集合 ai_settings 尚未创建"。
4. **修 `goBack` 被覆盖**：`utils/page.js` 在 `Page({...definition, ..., goBack(){...}})` 里位于 `...definition` 之后，同名键后者胜 → 页面自定义的 `goBack`（未保存拦截）是死代码。改名为 `onBack` 并同步 wxml `bindtap`。

### 结论性事实

- `get` 在 `ai_settings` 集合不存在时**能正常返回默认值**（`readStored` 吞异常，已实测），所以报错不是集合缺失；但 `save` 必须集合存在。
- 控制台「云端测试」调 `{"action":"get"}` 会返回 401，因为 `getWXContext().OPENID` 为空，属正常现象，不要当成故障。

基线：111 / 104 / 7，pages 20，check-project errors 空。

## 二轮：仍报 400 → 彻底删除“多余字段”校验

页面已能显示真实原因，返回 `400`。`get` 分支只有 `unexpected()` 一处会返回 400，说明云端跑的仍是带全等校验的旧代码；上一版只把 `userInfo` 加进例外名单，等于赌平台只注入这一个字段——只要多注入任何一个，get/save/reset 依旧全挂。

**改为彻底删除该校验**（`unexpected` / `IGNORED_KEYS` 全部移除）。安全性本来就不靠它：`stored` 是按白名单显式重建的，`{...event}` 从未落库。实测 `get + userInfo + _source + env + $something`、`save + extra + foo`、`reset + junk` 全部 `code: 0`；缺字段仍 `INVALID_PROMPT`、超长仍 `PROMPT_TOO_LONG`、未知动作仍 `INVALID_ACTION`。

配套：
- `response()` 增加 `build: 'ai-settings-2'`，用于判断云端跑的到底是哪一版（控制台搜这个字符串即可）。
- `utils/api.js` 把云函数返回的 `message` 挂到 `error.serverMessage`；页面 `failureHint` 据此区分 `INVALID_SETTINGS`(旧版) / `INVALID_ACTION`(部署错函数) / 其他。

结论：新代码下 `get` **只可能**返回 0 / 401 / 503，不可能再 400。若部署后仍见 `INVALID_SETTINGS`，只能是上传没落到这个函数上。
